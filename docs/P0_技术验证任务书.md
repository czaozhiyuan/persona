# persona — P0 技术验证任务书

> 阶段：P0 / 技术路线验证  
> 性质：一次性、可运行的纵向原型；不是 V1 正式开发任务书  
> 目标交付：可运行源码、单文件 HTML、示例工程 JSON、验证结果报告  
> 执行对象：Codex / 开发 Agent

## 1. 项目目标与 P0 定位

persona 是面向个人使用的**光电传输设备可视化设计与经验指标预算工具**。它将机箱 2D 布局、器件与 PCB 端口定义、光/RF 连接拓扑、可复用的层级模块、端到端命名链路及简化工程计算结合起来。最终使用方式优先为**一个可离线打开的 HTML 文件**，工程数据用独立 JSON 文件导入、导出。

P0 的目的仅是通过少量真实交互和计算案例，验证关键技术路线能否同时成立，并确定 P1–P5 所需的稳定数据边界；**不追求完整功能、正式 UI、复杂校验或生产级代码**。P0 的代码允许在后续重构或重写，不能为了兼容 P0 原型而牺牲正式架构。

## 2. 已确认的产品约束（P0 不得擅自扩展）

1. 使用 React + TypeScript + Vite 进行模块化开发，优先试用 **React Flow（xyflow）** 绘制逻辑拓扑、**React Konva** 绘制机箱俯视布局。Agent 可在验证后提出替代方案，但须说明原因和证据。
2. 最终构建输出一个可通过 Windows Chrome/Edge `file://` 双击打开的**完整离线 HTML**，运行时不得依赖本地 HTTP 服务、Python/Node 后端、CDN、外部字体或在线 API。可优先尝试 `vite-plugin-singlefile`。
3. **逻辑结构与物理布局互相独立**，通过稳定的器件实例 ID 关联；逻辑模块并不强制对应一个物理盒子。
4. 经验模型**只有一套**：固定参数、分段线性 RF 频率数据和离散光通道表均属于统一经验参数表达；不加入物理/简化物理模型选择、复杂数值仿真。
5. RF 扫描为一维频率扫描，默认且 P0 固定步长 **1 GHz**；内部计算保留浮点精度，输出显示到 0.1。光参数仅查询有效枚举通道，不进行任意波长连续扫描/插值。
6. 光系统分为 `MM850`（850 nm）、`CWDM`（标准 20 nm 间隔的合法通道枚举）、`DWDM_100G`（100 GHz 频率栅格的合法通道枚举）。CWDM UI 可显示工程习惯名称（如 1370、1390），数据结构要能稳定对应标准中心波长（例如 1371、1391 nm）。DWDM 通道编号采用明确的映射表；P0 至少包含 CH28 和 CH30；不得把二者误认为相隔 100 GHz。
7. RF 增益/插损用 **dB**，RF/光功率用 **dBm**，频率用 **GHz**，波长用 **nm**，物理尺寸用 **mm**。
8. 光电跨域采用**整段经验转换参数**，不展开 MZM/PD 物理计算。例如基准 RF 增益 `-22 dB`、基准 PD 接收光功率 `P_ref`，光路变化后的经验修正：`G_rf = G_ref + K × (P_pd - P_ref)`，`K` 默认 2.0 且可配置。只修正 RF 增益，不根据该式凭空推算 NF；不重复累计已包含在整段基准值中的光损耗。
9. PCB 是不展开内部芯片的黑盒器件，可定义任意多个 RF、OPTICAL、DC_POWER、CONTROL 类型端口及**明确的端口间经验传输关系**。未定义关系的端口默认不连通。
10. `Connection`（相邻端口的连接）、`Link`（用户命名的端到端逻辑路径）、`Channel`（光通道）必须区分；同一物理光纤可以承载多个 WDM 通道，多条 Link 可以共用器件或连接。
11. 不涉及 3D、BOM、PCB 内部详细电路、复杂时域/噪声仿真、用户管理、多用户、后端数据库、商业部署。

## 3. P0 实施原则

- 个人项目：**不开发账号、权限、多人协作、服务端数据库**。
- **不做旧版本工程兼容和迁移**；P0 只约定一个当前 JSON 结构，可保留简单 `schemaVersion` 字段，不实现迁移系统。
- **不建立大型测试体系**；只运行几项能验证核心假设的自动测试或手工验收。
- **不提前做过度架构抽象**；仅分离必要的项目模型、渲染、计算和文件读写。
- **不编制正式 PRD、不组织复杂设计评审**；P0 完成后再制订 V1 阶段任务书。
- 遇到与本任务不相关的功能，请记录为后续建议，不在 P0 顺手开发。

## 4. P0 必须完成的验证场景

### V01 — 单 HTML 构建及离线运行

- 使用分模块的 TS/TSX/CSS 源码构建，最终产出一个 HTML 文件；所有 JS/CSS 和必要静态资源均内嵌。
- 在**关闭网络**、不启动开发服务器的情况下，通过 Windows Chrome/Edge 直接打开 HTML，两个编辑视图及基本计算均可正常使用。
- 支持通过文件选择器**导入 JSON 工程**，通过浏览器下载**导出 JSON 工程**；不以 IndexedDB/浏览器缓存作为唯一工程存储。
- 验证中文界面、基本交互、导入导出能够在 `file://` 下正常使用；若有浏览器 API 限制，记录事实与替代方案。

### V02 — 双视图与统一实例 ID

- 展示一个简化的 1U 机箱俯视图（以 mm 定义平面尺寸；高度可作为机箱属性，不做 3D）。
- 提供激光器、MZM、PD、PCB、电源等示意矩形，能拖动定位，至少能修改位置和 90° 旋转。
- 逻辑拓扑视图显示相同器件的节点、端口和连线；两视图引用相同实例 ID，但保存**独立的布局坐标**。
- 在物理视图移动器件不改变逻辑连接；在逻辑视图调整节点不改变物理位置；修改某实例名称能在两个视图中同步体现。
- 不要求碰撞检测、自动布线或精美绘图 UI。

### V03 — PCB 多种端口及有效连接

- 示例 PCB 同时具有 RF_IN/RF_OUT、OPT_IN/OPT_OUT、DC_IN、CTRL_IN 等端口；端口数量可配置，不写死在组件 UI。
- 仅允许符合端口类型/方向规则的连线；演示至少一次有效连接和一次不兼容连接提示。
- PCB 至少定义一个 `RF_IN → RF_OUT` 经验增益关系，以及一个 `OPT_IN → OPT_OUT` 插损关系；没有关系的端口不参与传播。
- POWER/CONTROL 端口至少能建模、显示和连线；P0 不要求实现完整电源树或控制协议。

### V04 — 层级定义、实例化和参数覆盖

- 创建一个 `TX_Module`，包含至少两个内部器件以及模块输入/输出端口的映射。
- 在顶层**实例化两次**，证明实例不同、共用同一模块定义；实例可分别覆盖合法参数（如波长、激光器输出功率），互不串扰。
- 修改一次模块定义的共同参数/内部连接，两个实例同步更新；不要求在 P0 实现复杂的模块编辑 UI，可以通过简单控件或加载 JSON 演示。
- 支持跨一个层级的端口映射和路径追踪，不把 React Flow 的视觉 Group 当成模块定义机制。

### V05 — WDM、命名 Link 和共享连接

- 构造两条不同 DWDM 通道的 RF→光→RF 链路（例如 `RF_CH28`、`RF_CH30`），经过 MUX、**同一段光纤 Connection**、DEMUX，再分别到达各自终点。
- MUX/DEMUX 按标准通道 ID 进行明确的端口映射，光功率/插损按**当前通道表值**查找，不做任意波长插值。
- 每条 Link 保存稳定 ID、自定义名称、起止端口以及必要的路径/通道约束；选择 Link 时高亮其经过的节点和连接，显示路径及计算摘要。
- 修改一个通道的器件插损，另一条通道不应无故变化；共用器件/连接不能被复制成两份物理资源。
- 选择无法连通或存在歧义的路径时明确提示；P0 不要求全图枚举所有潜在路径。

### V06 — 经验计算与 1 GHz 扫描

- 演示一条有 RF 输入、MZM、光纤/光衰减器、PD、RF 输出的跨域链路；基准 RF 增益 `-22 dB`，`K=2.0`。
- 验证：在**只增加 3 dB 光衰减**、其他条件不变时，该 RF Link 的增益从 `-22 dB` 变为 `-28 dB`（等效 RF 插损从 22 dB 变为 28 dB）。注意参考光功率保持固定，不能随着每次重算重置。
- 验证：插入等效 +3 dB 的光增益且无其他变化时，RF 增益相对基准增加 6 dB。P0 可不模拟器件饱和。
- 对一个 RF 增益参数提供频率折点表（可使用 1、3、5 GHz 三个折点），在 1–5 GHz **每隔 1 GHz** 计算一组数值并生成表格/曲线，核对 2、4 GHz 的线性插值结果。
- 对缺失必要参数、通道不支持、超出 RF 曲线有效范围显示“无法计算/部分有效”，不得静默用零值填补；可以继续计算不依赖缺失参数的指标。
- P0 的 NF 可仅演示一个纯 RF 级联用例，按线性噪声因子公式计算；**不强求**完整光电链路 NF 预测。可显示单个端口/逐级/端到端的光功率与 RF 增益摘要。

### V07 — JSON 往返保持一致

- 将上述示例工程导出为 JSON 后，清空当前工程再导入，核实实例 ID、模块定义、参数覆盖、各视图坐标、端口、Connection、Link 名称及 DWDM 通道映射均保留。
- 使用纯数据层接口完成解析、路径查询和指标计算，**计算代码不能直接依赖 React Flow/Konva 的图形节点对象**。
- 无须设计多版本迁移、历史兼容及数据库 schema。

## 5. 建议的最小数据实体与代码边界

仅要求实现满足验证的最小字段，字段名由 Agent 选择，但必须区分：

| 数据对象 | 核心含义 |
|---|---|
| `Project` | 工程元信息、模块定义、器件实例、连接、命名链路、物理/拓扑视图数据 |
| `ComponentDefinition` | 器件类型、端口模板、尺寸、经验参数/通道表、传输行为 |
| `ModuleDefinition` | 可复用的模块内部网络、对外端口及映射 |
| `Instance` | 定义引用、独立 ID、参数覆盖 |
| `Port` | 稳定 ID、类型、方向、可选通道约束 |
| `Connection` | 两端口之间的单段连接，及可选线缆插损 |
| `Link` | 用户命名的端到端路径及约束、解析结果 |
| `OpticalChannel` | MM/CWDM/DWDM 的合法通道 ID 与中心波长/频率映射 |
| `LayoutState` | 实例物理坐标和逻辑节点坐标分别保存 |
| `CalculationResult` | 逐级与端到端结果、状态及报错信息 |

建议至少拆分为 `model/`、`engine/`、`editors/topology/`、`editors/layout/`、`storage/`，但 P0 不强制具体目录。引擎使用 TypeScript 纯函数/模块，优先保证可从独立 JSON 调用，不为预想中的扩展写大量接口层。

## 6. 明确不属于 P0 的工作

完整器件库管理 UI；所有 CWDM/DWDM 器件模板；批量属性编辑；自动布局/自动走线；3D、PCB 内部原理图；复杂功率树、电源效率级联；OSNR/ASE/RIN 物理仿真；非线性饱和；通道联合优化；权限/协同/数据库/云服务；MCP/CLI 集成；精美报表；复杂撤销重做；旧工程迁移；大规模自动化测试；性能极限优化。

> 波长枚举的基础数据表应正确且可扩展，但 P0 的交互验证只需少量真实通道；不能因为示例仅有 CH28/CH30，就把合法通道体系永久写死为这两个值。

## 7. 验收方式

P0 验收以**真实可运行原型及结果证据**为准，至少检查以下事项：

| 编号 | 最低通过标准 |
|---|---|
| A1 | 单 HTML 在断网 `file://` 方式打开，编辑、计算、JSON 导入导出可用 |
| A2 | 物理/逻辑双视图共用实例 ID，坐标和连接互不干扰 |
| A3 | PCB 支持 RF/OPTICAL/DC_POWER/CONTROL，多端口及基本连接校验 |
| A4 | `TX_Module` 两实例复用、参数覆盖、定义修改同步有效 |
| A5 | CH28/CH30 共享物理光纤，两条命名 Link 可分别追踪和高亮 |
| A6 | 跨域光衰减 -3 dB 导致经验 RF 增益 -6 dB，且无重复扣除 |
| A7 | 1 GHz RF 扫描点齐全，分段线性插值正确 |
| A8 | JSON 重新导入不丢失核心实体关系和命名链路 |
| A9 | 数据模型和计算引擎能脱离图形界面执行基本计算 |

若某项未通过，应报告：复现步骤、根因（如已知）、影响范围、可选替代方案和推荐决策；不要为了让验收表变成“全部通过”而虚构结果。

## 8. 交付物

1. **源代码**：含可复现构建指令和简短 `README.md`。
2. **最终单文件 HTML**：可离线双击打开。
3. **示例工程 JSON**：覆盖上述核心场景。
4. **P0 验证报告 Markdown**：逐项填写 A1–A9 的真实通过/失败/部分通过情况，并记录关键截图或操作说明、依赖版本、构建与离线测试方法、已知限制。
5. **P1–P5 架构建议（简短）**：应继续使用哪些库、哪些需调整，正式任务书应冻结哪些数据和接口边界。不写详细的后续任务书。
