# P1–P5 架构建议

P0 的证据支持继续采用 React + TypeScript + Vite、React Flow、React Konva、vite-plugin-singlefile。两种画布均已在同一离线单 HTML 中运行，暂没有替换库的实证理由。正式实现可重构原型代码，不应为兼容 P0 工程保留历史负担。

| 阶段 | 建议冻结的边界 |
|---|---|
| P1：工程模型 | 稳定 ID、单位、端口类型/方向、显式 Transfer、Connection/Link/Channel 的区别；JSON 只约定当前结构，先不做迁移系统。P0 的 `:`/`/` 路径分隔是实现约定，正式版应明确合法字符或采用结构化端点。 |
| P2：双视图编辑 | 两份 LayoutState、统一实例 ID、共享名称；编辑器只读写领域数据，不让引擎接收 React Flow/Konva 对象。物理模块装配关系应独立于逻辑 ModuleDefinition。 |
| P3：模块与路径 | 定义/实例/覆盖的合法范围、内部实例命名空间、对外端口映射、通道匹配、不可达/歧义及必经连接的结果协议；需要时再扩展层数。 |
| P4：经验预算 | 固定值/RF 折点/离散光通道的统一表达；明确增益有符号、插损展示规则、参考光功率与 G_ref 的测量条件及唯一归属，禁止重复损耗。保持缺失、有效范围、部分有效及 NF 不可用的状态。 |
| P5：交付验收 | 锁文件、单文件构建、第三方许可、离线 `file://` 回归、JSON 往返及最小人工验收；以实际使用的 Windows 浏览器版本验收，避免把原型软件算例当成真实器件标定。 |

优先调整的是 P0 为演示硬编码的属性面板（`laserPowerDbm`、共同 MZM 控件等）：正式版应依据已确定的定义参数生成最少必要控件。模型、计算、存储和编辑器四个边界应保留；暂不引入大型插件框架、服务端、数据库或通用物理模型。

进入 P1 的前置决策：补完 A1 人工断网双击验收，确认 TX 整段经验基准的标定口径，以及器件尺寸/原点和通道编号约定。其余后续功能按实际需求另立任务，不扩展到当前 P0。
